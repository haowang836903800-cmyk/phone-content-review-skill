# 飞书内批注、视频修改意见与复审回写

适用：用户指定某份豆包手机稿件，要求审核并把意见直接留在飞书。用户已选择本工作流时，审完直接执行与回读；若只要求学习、打包或只分析，不执行写入。

## 1. 固定目标并读取上下文

读取可用 `lark-doc`、`lark-drive` 技能及对应操作reference。优先CLI/连接器；缺少原生播放器时间轴能力时可使用可见UI，但不猜未公开接口。

保存一次本地运行记录：原始URL、实际文档token/type、达人、送审版本/更新时间、文档revision、视频附件token/文件名/时长/本地hash、用户授权模式、实际读取/观看范围。存工作目录，不放认证信息到skill或GitHub。

抽帧、ASR及播放记录都绑定同一份媒体清单：源文档与附件token、原文件名、SHA-256、准确时长、产物路径、采样/播放方式与区间。工具临时命名的v1不等于送审V1；文档标题“V2视频”也可能装着v4.mp4。缺来源绑定时先核对原附件，不拿未经确认的时间码直接发评论。

```bash
lark-cli docs +fetch --doc '<原始稿件URL>' --detail full --as user
lark-cli drive +list-comments --url '<原始稿件URL>' --solved-status all --need-relation --page-size 100 --as user
```

本工作流复盘历史修改，需同时读取已解决与未解决意见。按外层 `has_more` 翻页；单卡若仍有回复，用 `drive +list-replies` 继续分页。不要把根回复、普通回复、评论卡混为一个ID。

甲方/机构已有同一问题时，优先补必要的复核结果；没有新信息不重复留言。文档版本或视频不唯一时，先确认送审对象，可继续给不依赖版本的意见，但不要猜评论落点。

## 2. 形成意见与写入计划

先做内容判断，再决定如何落批注。每项保留：问题、原句/时间点、依据类别、具体改法、复审验收、目标block/评论ID、操作类型。结构见 `assets/comment-plan.schema.json`。

每个文档独立一个计划。多稿合在一个JSON时可用 `plans` 数组，但每个子计划必须单独通过单文档schema；不能共享一个doc/version字段后把操作混在一起。模式、`execution_allowed`、真实当前作者、每条证据状态与写前条件必须明确。离线/模拟计划固定不可执行，不因为字段叫planned就交给写入工具。

待原音确认的疑似台词、尚未绑定版本的抽帧问题，先由审核者补核，再决定是否投递。不要直接把“ASR好像说了这个，如果说了就改”的预备意见当已核问题发出去。确实缺素材时，可以写清已确定的材料缺口，索要对应文件，不据未核台词判错。

脚本优先挂在对应段落/表格内具体文字块；同一块可在评论正文引用原句。块级定位不冒称逐字选区。重名/重复台词靠block与上下文区分，不用第一个搜索命中代替定位。

写入前重读目标block及相关评论，检查引用文字、视频token和上轮意见是否变化。远端有并发改稿时重算判断与锚点，保留对方改动。

XML里的figure ID与source ID可能属于不同导出层级。结合当前API块信息和评论relation确认可评论block，不能任选一个；本地看见ID不等于锚点已验证。写后仍需回读位置。

## 3. 脚本批注

一条批注讲一个可以执行的问题，相关的同类修改可合并。完整内容以纯文本或结构化元素提交，少用Markdown语法。

> 我方初审｜脚本V2｜需修改
>
> 原句：……
>
> 这里的问题：……
>
> 建议改成/拍成：……
>
> 复审看：……

推荐 `--content @./comment-01.json`，文件内容为 `[{"type":"text","text":"完整评论正文"}]`。用JSON编码器写文件，或用Python `subprocess.run([...])` 的参数数组传入；不要把达人文本插进shell代码。

```bash
lark-cli drive +add-comment --doc '<原始稿件URL>' --block-id '<实时读取的block_id>' --content @./comment-01.json --as user --dry-run
lark-cli drive +add-comment --doc '<原始稿件URL>' --block-id '<同一block_id>' --content @./comment-01.json --as user
```

预检不等于实际评论完成。缺精确文字选择时使用已核对的段落block，并在评论里引用原句；不要跳过局部定位，把所有问题塞成一条全文评论。

## 4. 视频意见的落点

| 送审素材 | 实际写法 | 不能声称 |
|---|---|---|
| 文档内视频/文件附件 | 在对应附件block创建局部评论；内容写文件名、版本和时间区间 | 不能说已创建播放器原生时间轴批注 |
| 有对应“视频修改意见”段落且附件块不可评论 | 精确挂到该段落，写明视频来源、版本和时间点，并向用户说明落点 | 不能误挂旧视频或随便别的段落 |
| 独立Drive MP4文件 | 查实时支持后用文件全文评论，每条意见注明时间点 | 当前CLI不提供该文件的原生逐帧锚点 |
| 单独抖音链接/本地视频，尚无审核文档 | 先审并输出意见；定位本次明确授权的稿件文档，缺目标时询问 | 不去抖音评论区发审稿意见，不新建无关文档替代 |

> 我方初审｜视频V3｜文件：送审V3.mp4｜00:16—00:23
>
> 当前画面只有会议摘要，字幕写“已经发进飞书”。请补目标文档和分享完成画面，拍清责任人、任务、期限；若实际只生成摘要，就把表述收窄到整理出清单。

时间码必须来自这一版实际观察。截图/ASR无法核验的原声、自然语气或完整操作，要具体注明待核；仍可发布有证据的视觉问题与补看要求，但不作全片通过结论。视频时长不等于任务完成用时。

## 5. 复审、回复和修改已有评论

复审先列“上轮要求→本版变化→是否落实”。问题解决就记录解决依据；仍有差距就回复具体差距。不要自动替甲方点已解决。

```bash
lark-cli drive +list-replies --url '<原始稿件URL>' --comment-id '<已读取的comment_id>' --as user
lark-cli drive +add-reply --url '<原始稿件URL>' --comment-id '<对应未解决局部评论ID>' --content @./reply.json --as user
lark-cli drive +update-reply --url '<原始稿件URL>' --comment-id '<comment_id>' --reply-id '<核实为我方当前身份的reply_id>' --content @./updated-reply.json --as user
```

- 更新是整体替换。先留存原内容、作者与更新时间，明确是根评论还是普通回复；只更新本次指定的、当前身份拥有的那一条。身份相同不代表所有历史评论都在授权修改范围。
- 根回复是第一页面最早创建的reply，不是每页第一条；更新根回复等于改评论正文。用户已指定“更新我的这条审核意见”且定位明确时可执行；没明确改哪条时先新增复审回复，不静默覆盖历史。
- 不能修改雷、达人或机构其他人的发言。对其意见有不同判断时，以我方身份回复事实与改法。
- 当前CLI不能回复全文评论或已解决评论。遇此限制，不擅自恢复甲方评论；确需补充本次复审意见时，在同一已核验内容block新建局部批注并说明与上轮意见的关系。明确指定“只回复这一条”而不可回复时，报告限制，不换地方偷发。
- 同一问题、同一版本已存在我方相同意见则跳过；有新证据再回复。对已修好的片段不重复提改。

## 6. 写后回读、失败与去重

每次写入串行执行，保存返回的 `comment_id/reply_id` 后再做下一项。成功看JSON `ok=true`，并继续回读，不能只靠退出码。

```bash
lark-cli drive +batch-query-comments --url '<原始稿件URL>' --comment-ids '<返回的ID>' --need-relation --as user
lark-cli drive +list-replies --url '<原始稿件URL>' --comment-id '<对应ID>' --as user
```

核对正文、作者、文档、版本提示和锚点。`relation.relation` 是JSON字符串，其 `positionInfo.blockID` 与实时block对应才算锚点已核；`content_deleted=true` 不算准确落在现存内容。回读不含位置就补查或通过可见UI核对，并如实报告定位粒度。

本地回执以“文档token＋送审版本/媒体hash＋block/时间区间＋问题类型＋评论正文hash”为去重键。重跑时结合远端已有评论验证，不能只依赖本地记忆。

网络超时/断连时先按已知ID或该段评论查是否写入，避免直接重复POST；连续两次无法查清则停止该项，记录“结果未确认”，继续不依赖它的只读分析。权限不足、身份错误、锚点失效分别修正，不盲重试或切身份扩权。

最终简报只报实际回读通过的条数和文档链接，另列未写入/结果未确认项。评论内容短而可执行；完整依据和回执保留在本地，不给达人倾倒运行日志。
