# 每周增量学习与GitHub更新

用户授权：每周学习新增且此前没看过的已发布脚本、甲方批注、修改及视频，同时学习新的推广方向、Brief和玩法；完成后自动更新本技能及指定GitHub仓库。默认计划是每周一10:00，Asia/Shanghai。具体执行时间以Codex Automation为准，修改计划使用自动化工具，不手写cron文件。

这是学习模式，不是重新审批或给已发布历史稿件发评论。默认不改客户/机构表状态，不发群消息，不发布视频。

## 固定来源与可移动路径

从 `sources.json` 读取项目文件夹、周度Brief文件夹、甲方表和测试表。把当前仓库根目录设为工作目录，必要时在其外建立原始材料缓存；不要把本机用户名、绝对缓存路径或凭证写进可分发技能。

GitHub仓库记录于 `sources.json` 的 `distribution.repository_url`。每次推送前核对remote、仓库owner和私有状态。不要推送到相似名字的其他项目，也不自动改可见性。

## 1. 比较本次数据与学习台账

1. 全量读取当前甲方表中“已发布”的记录，完成分页；保留原记录ID、稿件/发布URL、发布日期和数据更新时间。不要只截“最近7天”：晚填、补发、状态迟更新都可能漏掉。
2. 与 `learning-state.json` 以 `record_id` 比较。昵称不是唯一键。没有记录的已发布条目进入新学队列；记录存在但稿件版本、附件、评论或相关要求有变化，进入差异复查队列。
3. 脚本源用实际document token与revision/content hash；批注保留可比较的评论/回复版本指纹；视频以附件token/文件名、可得的hash和送审版本对应。不能把文件排序变化误认新内容。
4. 旧83条基线为“已学习但有核验范围限制”，不是完整人工听看认证。优先新增、变化和影响当前结论的待核项；不要每周把所有旧视频无差别重跑。
5. 同时刷新周度Brief目录、机构版BF、达人版BF、机构红线正文及承载要求的图片/附件、新增项目要求/会议结论、测试表状态/实测结果/失败环节/是否可推。即使没有新发布，也查规范是否变更；不要只看文件名和标题。冲突逐条保留来源与适用日期。

文档/批注指纹统一用 `scripts/fingerprint_sources.py`，输入为本地保存的 `docs +fetch --detail full` 与已收齐全部分页、回复的 `drive +list-comments` JSON。脚本不联网、不写入、不宣称学习完成；分页未收齐或两个来源不是同一文档会报错。它保留正文、作者、锚点、解决状态、回复内容，忽略单纯排序、抓取元数据和更新时间变化；依旧要逐项判断差异是否影响审核。

```bash
python3 scripts/fingerprint_sources.py --doc '<本地文档JSON>' --comments '<合并完分页的评论JSON>'
```

以输出的 `content_sha256`、`comments_sha256` 比较基线同名字段。`comment_snapshot_sha256` 只是旧原始响应存档指纹，不能与新规范化值混比。脚本没有检查视频和其他来源，这些仍按附件token/版本及真实内容核对；表内互动数变化不等于稿件变更，影响复盘时单独更新数据观察。

## 2. 学新案例必须完成的内容

- 读当前脚本及可读取的已解决/未解决批注与完整回复，区分雷、其他评论者和我方推断。
- 选取能解释改变的历史版本，核“为什么改→改了什么→当前是否落实”；不必把每次自动保存当一个独立版本。
- 查看实际视频与重要改稿版本。记录完整播放/分段播放/抽帧/转写的真实覆盖；缺少声音或关键结果时留缺口，不编语气与成效。
- 核对公开发布链接及可访问的评论和数据，区分表内与公开页时间，记录加热未知、基线缺失，避免用互动倒推正确性。
- 提炼至少一个有依据的判断：适用条件、可借鉴片段、不能照搬之处、对既有规则是新增/例外/修正/无变化。

普通案例只更新案例库；多案例或最新明确要求才提炼入通用手册。新玩法“已跑通”也要读结果和是否可推，不从空字段推导发布许可。

## 3. 更新文件与验收

- `references/casebook.md`：增量加入新案例，编号从已有最大值继续，保留旧来源；已学案例仅更新新版本对应观察，不覆盖成无历史的结论。
- `references/revision-cases.md`、`reviewer-handbook.md`、`brief-and-redline-map.md`、`creator-guide.md`、`capability-boundaries.md`、`selection-and-optimization.md`：只改确有新证据影响的条目。
- `references/sources.json`：记录当前来源和刷新日期。
- `references/learning-state.json`：逐项登记学习状态、源版本、检查范围、未完成事项和本次检查时间。某一条未完成就保留pending/partial，不整体推进成“全部学完”。
- `updates/YYYY-MM-DD.md`：记录新增/变化/无变化数量、关键规则变更、例外、待核验内容和本次实际覆盖。不含凭证或原始大视频。

用真实且不同的审稿输入检验变更是否造成误判：自然长内容不被专项30秒规则误杀、改好内容不重复批、视频缺证不假通过、周更不产生稿件评论。结构校验通过不等于审核准确率通过。发现反例先修正，不机械堆新规则。

没有新增案例，也必须检查Brief与测试表。全部没变化时只更新本周检查记录，不凑出“新发现”。

## 4. 同步本机与GitHub

1. `git fetch`，核对当前分支与远端；本地有无关改动或远端有并发提交时先保留并整合。不要force push，不覆盖别人新写的内容。
2. 阅读diff，检查来源依据、模板引用、JSON、技能frontmatter、敏感信息与文件范围。只提交技能、必要知识、台账和本周更新说明。
3. 校验通过后更新本机同名安装技能，保存必要备份并回读文件hash。再提交/push到本仓库默认分支。
4. 从GitHub回读默认分支head与关键变更文件，确认commit SHA/内容；只看到本地commit或push命令启动，不算GitHub已更新。
5. 若push超时，先查远端head再决定重试。拒绝、权限故障或冲突不能伪装成功；保留本地成果，报告具体待处理项。下周接着未完成项，不重复生成相同提交。

最终只汇报本周新增/复查数量、更新的审核规则、仍未完成的证据缺口、GitHub提交链接。使用当前对话/自动化结果通知，不额外向飞书群广播。
